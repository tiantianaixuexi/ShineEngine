## 3. 目录层级与模块化（扁平化 vs 分层）

### 3.1 现状结论

- 构建系统已具备 target-based 雏形（JSON 驱动模块 + target 链接）
- 但主目标 `MainEngine` 仍依赖 `src/**` 全量收集 + 排除法，目录重排成本高
- `src/third` 与引擎源码同根，语义层级混杂

### 3.2 方案对比

#### A. 扁平化（浅层目录 + 功能前缀）

- 迁移成本：低~中（约 2~3 Sprint）
- 优点：路径短、跨模块检索快
- 缺点：大型工程后期边界回退，易再次“混层”
- 适用：团队规模小、快速迭代阶段

#### B. 分层（foundation / runtime / editor / app）

- 迁移成本：中~高（约 4~6 Sprint）
- 优点：依赖方向可治理，便于拆库与 CI 分层
- 缺点：初期改造量大（include + Module JSON + 依赖梳理）
- 适用：中长期可维护性优先（推荐）

### 3.3 clang-build-analyzer 量化数据状态

- 当前状态：环境缺少 `clang-build-analyzer` 可执行文件，无法产出真实编译热点报表
- 已定义采集口径：
  - Full Build Wall Time
  - Frontend Parse Time Top-20
  - Header Parse Fan-out
  - TU 重编译命中率
- 结论：本次给出迁移成本与收益模型；真实对比值需在 CI 预装工具后补采

## 4. 可封装与可复用性

### 4.1 底层能力拆分评估

- 已有可拆基础：
  - 序列化/编码：`util/encoding*`
  - 调度：`util/thread/*`
  - 内存：`memory/*`
  - 日志：`EngineCore/log/*`
  - 反射：`EngineCore/reflection/*`
- 主要问题：
  - 与 editor / manager 层存在双向或跨层 include
  - 还未形成“底层 target 先行、上层仅依赖接口”的硬约束

### 4.2 God-Object 候选

- `editor/mainEditor.*`：窗口编排 + 生命周期 + 业务触发集中于单类
- `manager/AssetManager.*`：加载、缓存、纹理桥接、生命周期管理职责过多
- 建议：提取接口层 + 依赖注入
  - `IEditorShell`, `IAssetCatalog`, `ITextureBridge`, `IImportPipeline`
  - 由 DI 容器（组合根）组装，UI 层不直接 `new` 具体实现

### 4.3 覆盖率目标可达性

- 目标“单测覆盖率 ≥ 90%”建议分层施行：
  - 底层库（util/memory/reflection）：90%+
  - 业务编排层（editor shell / world orchestration）：70~80%
  - UI 绘制层：快照测试 + 交互冒烟替代行覆盖

## 5. 性能热点与内存模型

### 5.1 Tracy 三场景（启动/导入/保存）现状

- 已集成 Tracy 宏与文档，但缺少三场景标准化采样产物（`.tracy` 会话与 Top-10）
- 结论：本次无法“伪造 Top-10”；需按统一脚本采样后补齐

### 5.2 代码级高风险项

- 大文件与高复杂度集中：`png.cpp`, `jpeg.cpp`, `objLoader.cpp`, `gltfLoader.cpp`, `file_util.cpp`
- 重复状态机与字符串拼接路径较多（导入、清单构建、日志拼接）
- 异常/RTTI 使用整体不重，但错误路径仍可统一为 `expected/error_code`

### 5.3 修复模板（Clang-Tidy + PVS）

- 容器：`reserve/emplace`、避免中间容器复制
- RTTI/异常：减少动态类型分发，约束热路径异常
- 字符串：优先 `shine::SString` + 预分配 + `fmt::memory_buffer`
- 序列化：引入 view/零拷贝写入接口，避免多次 `std::string` 拼接

### 5.4 pmr 改造建议

- 在导入与清单构建热路径引入 `std::pmr::monotonic_buffer_resource`
- 目标 KPI：分配次数下降 ≥30%，导入耗时下降 ≥15%
